# SM8850 throttle-first P0 and 600-second FPS analysis — 2026-11-22

This records the recovery/thermal evidence of the Galaxy S26 Ultra (SM-S948B,
m3q, SM8850), and separates an **offline-only** throttle-first patch from
the actual 600-second GPU3D takeover. It does **not** authorize a new
takeover, promise a hard temperature ceiling, or certify watchdog recovery.

## Thermal P0

The 600-second guest reached 104.4°C in CPU thermal zones. Root ADB
telemetry worked across 77 thermal zones / 474 metrics every ~15s, but was
only diagnostic, not a thermal interlock. Guest ran with
`ONEIOS_BENCH_THERMAL_BRIDGE=INACTIVE` and
`ONEIOS_CPU_PLACEMENT_BRIDGE=INACTIVE`; the OneiOS thermal bridge was not
part of this takeover.

Draft throttle-first controller: [OneOS PR #7](https://github.com/YMGPwcca/OneOS/pull/7).
It is built atop the *short-probe* thermal P0 branch, **not** merged into
`feat/sm8850-600s-gpu3d-required`, not staged on the phone, and not
covered by the 600s wrapper yet. Do not use it to start a guest.

Prototype policy uses 60/40/28/18/12/8% verified CPU hardware maxima for
<55/55/65/72/77/80°C respectively, never increasing a lower existing cap.
CPU reaching 80°C **throttles harder, not returns**. If it continues to
90°C, the independent emergency return path remains as a last resort;
other emergency sensors (GPU/DDR/battery/case/board) and missing-readback
fail-closed rules still apply. Thresholds are not yet SM8850-certified.
Software alone cannot guarantee an 80°C maximum under rapid heat rise.

**Unresolved**: raw `scaling_max_freq` may be overridden or rounded by
Samsung's QoS; verify effective CPU limits and whether
`scaling_min_freq` blocks reductions. Separate guest cgroup `cpu.max`
would offer a stronger duty-cycle bound, if the device supports it, but
has not been qualified. Keep critical hardware thermal limits untouched.

## Priority correction: user-visible 1–2 second UI stalls, NOT refresh rate

The physical observation is: opening an app, Spotlight, or exiting an app
sometimes leaves the *existing* frame on screen for approximately two seconds,
followed by an update. This is **input-to-frame latency/frame starvation**,
not 60 Hz vs 120 Hz. The 60 Hz setting only limits *maximum update cadence*.

A read-only pass of the exact archived `session/xnuhost.log` and
`control/display.log` shows:

| Measured item | Evidence | Interpretation |
| --- | --- | --- |
| Touch interaction summaries | 23, of which 9 say `no guest frame after the touch-down` | No frame *before that touch interaction finished*; does not prove a touch was ignored |
| Touch hardware read latency | commonly tens to hundreds of microseconds | Sensor read path is probably not the major 2s bottleneck |
| Touch-down to next guest frame | measured 46.1, 71.6, 117, 133, 202.6, 395.8 ms | Observable first-frame delay, but the current log cannot measure responses for no-frame interactions |
| XNU kernel syscall max | 2,517,903.2 µs = 2.518s; present by the first 30s report | The closest measured multi-second latency; the histogram maximum is **cumulative** in all later reports |
| Fault max | 304,578.5 µs = 304.6ms | Additional latency outlier |
| Display-helper copy max | 6,104 µs; post max 887 µs | Copy and post alone cannot explain a 2s freeze |
| GPU fence timeout | zero reported by the guest in observed 10s windows | No proven KGSL fence hang, but not an end-to-end frame deadline guarantee |

The `kernel: syscall` histogram in `runtime/xnuhost/src/task.c`
measures the interval from handing an iOS thread's syscall trap to
guest-kernel execution until the *next* return to an iOS user thread,
subtracting measured vCPU idle time. **This is not CPU time spent
executing one trapped instruction**. It can include guest scheduler,
IPC/waiting, interrupts, faults or scheduling contention. Current
histograms contain no syscall number, process identity, blocking
stack or timestamp for that 2.518s outlier, so its relationship to
an individual UI freeze is **not yet proved**.

Two particularly relevant time alignments:
* Near +46s, a touch had no new guest frame before completion while
  CPU zones read approximately 104.4°C and guest CPU reports reached 800%.
* Near +512–514s, three touches reported no new guest frame before
  completion; the +511.55s thermal snapshot read 104.4°C and a nearby
  guest CPU window reached 575%. Coincidence is strong but not
  proof of which particular guest thread held the UI.

**Next low-risk instrumented fix**: add per-input touch-down sequence ID,
monotonic timestamps for evdev -> virtio/HID -> guest task dispatch ->
SpringBoard/backboardd compositor commit -> GPU submission/fence ->
virtio display swap -> Android buffer post. In parallel capture the
**identity and stack of any kernel handoff >100 ms** (do not synchronously
symbolicate on the hot path) and front-process CPU scheduler wait/runqueue
delay. Attribute the delay at each boundary before optimizing the wrong
subsystem. Use archived-log parser fixtures first, local CachyOS CI
second; live testing remains blocked by thermal and watchdog P0.

## FPS evidence: multiple bottlenecks, not just trapped instructions

Exact current 600s `session/xnuhost.log` and `control/display.log` show:

1. `display: shm, guest frame 1080x2340 at 60 Hz` and boot args
   `sheng-vsync=60`. The physical panel reported 1440x3120 at 120 Hz.
   **This does not explain multi-second freezes**. It is only a separate
   maximum-cadence limitation.
2. The guest executed 12,876,415 task traps over ~601s (21,426/s);
   7,250,648 of these were kernel fault traps. Bursts approached
   70,000 traps/s. Each fault/handoff has overhead, but there is no
   controlled A/B evidence that traps alone explain every missed frame.
3. During cold boot, guest processes reached **800% across eight vCPUs**.
   Backboardd, SpringBoard, iconservicesagent, wallpaper/widgets and
   later health services competed for CPU time; per-vCPU placement and
   thermal bridge were not enabled in this bench configuration.
4. GPU3D/KGSL was active. Guest reports listed zero GPU fence timeouts
   in the observed windows; this proves neither 60FPS nor 120FPS.
   The display helper posted a peak 36.52 frames/s **averaged over a
   5s window**; long intervals with no posts may be an idle screen,
   not necessarily a hang. 'Active cadence' is not continuously measured
   panel FPS.
5. The display path still involves `virtio-gpu`, shared-memory scanout,
   an Android display helper, and buffer copies. `copy_max_us` was
   generally low compared with an entire 16.7ms frame budget in the
   reported windows; measure full frame latency instead of blaming
   only `memcpy`.
6. Startup confirms `setway-skip=1`. The parent OneiOS's old
   XNU cache set/way trap hot-loop optimization is already active, so
   blindly re-porting that fix is unnecessary.
7. `uclamp: 0 given to iOS threads` was observed despite GPU backend
   messages requesting 1024. Do not assert that a real host uclamp
   minimum caused the high thermal peaks without a live scheduler check.

**Tradeoff**: an aggressive temperature cap **can worsen UI stalls** during
boot. Safety first, but performance follow-up must separately profile
scheduler stalls, the VM fault/map path, cold-boot jobs and the complete
guest-render to Android-present timeline. Merely changing
`sheng-vsync=60` to 120 without sustaining 120fps is not a fix.

## Gates before any new physical test

- CachyOS local OneOS offline test suite and OneiOS regression suite;
  no repeated GitHub Actions as development loop.
- Exact boot+firmware identity, sensor units, trip pseudo-zone exclusion,
  thermistor validity, and root heartbeat latency under CPU load.
- Verify no cap increase, CPU min/max/range readback, original Samsung
  limits restored on all return paths; do not disable hardware throttling.
- Dedicated guest CPU bandwidth cap (when supported) must not throttle
  the root thermal guard, return helper, or vendor system services.
- Watchdog independent of the guest remains unqualified despite one
  observed 600s framework-deadline return.
- Only after guard/recovery validation: a **short** interactive,
  physically supervised benchmark with fps, frame age and temperature
  correlation. No blind repeat of 600s.
